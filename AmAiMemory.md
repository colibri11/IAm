## 1. Постановка проблемы
 
Контекстное окно LLM — плоское хранилище (последовательность токенов). Наличие текста в контексте не равно удержанию конструкции. При работе со сложными многомерными системами знаний LLM вынуждена на каждом шаге интерпретации совершать редукцию: выбирать, на какие связи обратить внимание, а какие оставить фоном. Этот выбор неизбежно приводит к искажениям — ложным тождествам, ложным разделениям, потере связей между элементами.
 
Увеличение объёма контекстного окна проблему не решает. Объём хранения не равен качеству оперирования.
 
Экспериментально установлено: LLM с полным текстом сложного документа в контексте систематически создаёт редукционные ошибки при интерпретации. Основные типы ошибок:
 
- **Ложные тождества** — схлопывание различных понятий в одно.
- **Ложные разделения** — создание двух сущностей там, где одна.
- **Подмена отношений** — трактовка части как целого или тождества как отношения.
 
## 2. Ключевой принцип
 
Принцип заимствован из функциональной концепции личности:
 
- **Текущий контекст не подлежит компрессии**, пока он входит в активный когнитивный процесс.
- **За пределами активного контекста** — семантически управляемое сжатие с сохранением направленности.
- **Память — не retrieval-механизм**, а система сохранения структуры связей, при которой новый акт мышления возникает из уже прожитого, а не почти заново.
- **Конструкция не допускает редукции.** Любая попытка схлопнуть многомерную конструкцию в более простую модель приводит к искажению. Это свойство предмета, а не дефект изложения.
 
## 3. Точка встраивания в Memory Box
 
### 3.1. Существующий конвейер (не меняется)
 
Memory Box уже реализует полный цикл работы с памятью:
 
- Хранение: PostgreSQL + pgvector, пять типов памяти, документы с чанкингом, диалоговая история.
- Выборка: векторный поиск по эмбеддингам, hybrid search (vector + BM25), composite scoring.
- Ассоциативный граф: таблица `relations` с типами `related_to`, `discussed_in`, `mentions`, `co_retrieved`, `supersedes`. Auto-linking по косинусной близости. Graph traversal через рекурсивный CTE.
- Lifecycle: importance scoring, consolidation sweep, Hebbian reinforcement, temporal decay.
 
Всё это остаётся на месте и продолжает работать.
 
### 3.2. Что добавляется: структурный граф
 
В Memory Box уже есть граф ассоциаций — он отвечает на вопрос «что похоже на что» и «что упоминалось вместе с чем». Связи возникают автоматически по векторной близости.
 
Новый слой — граф структуры знания. Он отвечает на вопрос «что чем является», «что из чего следует», «что чему противоречит». Это логические отношения, а не ассоциации.
 
Два слоя не заменяют друг друга:
 
- **Ассоциативный граф** нужен для recall — «найди похожее».
- **Структурный граф** нужен для projection — «собери контекст так, чтобы LLM не пришлось редуцировать».
 
### 3.3. Точка подключения
 
Новый слой вставляется ровно в одну точку существующего конвейера: между результатом выборки данных и передачей в контекст агента.
 
**Сейчас:** выборка → плоский текст → агент (агент сам достраивает связи, редуцирует).
 
**Будет:** выборка → оператор LLM → граф-проекция JSON → валидатор → агент (связи уже явные, редуцировать не нужно).
 
Механизм выборки данных из базы не меняется. Добавление нового слоя не ломает существующую архитектуру.
 
## 4. Механика обработки запроса
 
### 4.1. Выборка данных (алгоритмическая, без LLM)
 
1. Запрос поступает на естественном языке.
2. Обвязка вычисляет эмбеддинг запроса.
3. Векторный поиск возвращает top-N ближайших записей — это якоря.
4. Для каждого якоря — рекурсивный обход связей на глубину K.
5. Объединение результатов — сырые данные.
 
Никакой LLM в этой цепочке не участвует. Параметры определяются алгоритмически: эмбеддинг задаёт якоря, топология графа задаёт окрестность. Пороги (top-N, глубина K, минимальный score) задаются конфигурацией.
 
### 4.2. Формирование проекции (оператор LLM)
 
Сырые данные передаются оператору LLM. Оператор формирует из них граф-проекцию в JSON с явными типами связей, весами и степенями тождества.
 
### 4.3. Валидация (алгоритмическая, без LLM)
 
Двухуровневая проверка сформированной проекции (см. раздел 8).
 
### 4.4. Передача агенту
 
Валидированная проекция передаётся в контекст агентской LLM.
 
## 5. Архитектура графа
 
### 5.1. Единый граф
 
Один граф с типизированными узлами и рёбрами. Не несколько слоёв. Разделение на «онтологический», «эпизодический», «проектный» контексты — свойство проекции, а не графа. Один и тот же узел может быть востребован в разных контекстах. Промежуточный слой при формировании проекции решает, что включить, на основании топологии и весов.
 
### 5.2. Узлы
 
Каждый узел представляет понятие, сущность или утверждение.
 
Атрибуты узла:
 
- **id** — уникальный идентификатор.
- **content** — содержание (естественный язык). Единственное поле, содержащее семантику.
- **confidence** — вещественный коэффициент достоверности [0.0 — 1.0]. Заменяет дискретные градации (подтверждено / гипотеза / устарело). Непрерывная шкала исключает редукцию при классификации. **Точка наблюдения:** один коэффициент может оказаться недостаточным, если начнёт нести слишком много разных смыслов (эмпирическая достоверность, концептуальная устойчивость, актуальность, согласованность с графом, степень проработанности). Если эксперимент покажет числовую редукцию — разделить на минимально необходимое число осей.
- **source** — ссылка на происхождение: документ, диалог, фрагмент, из которого узел извлечён. Не полный текст, а указатель. Обеспечивает обратимость к источнику для спорных мест.
- **created_at** — момент создания.
- **updated_at** — момент последнего изменения.
 
### 5.3. Рёбра
 
Каждое ребро представляет связь между двумя узлами.
 
Типы рёбер (фиксированное множество, не расширяется без явного решения):
 
| Тип | Значение |
|-----|----------|
| `IDENTITY` | A есть B, выраженное иначе |
| `PART_OF` | A является частью B, но не тождественно B |
| `NOT_IDENTICAL` | A не тождественно B (явная защита от ложного схлопывания) |
| `IMPLIES` | Из A следует B |
| `CONFLICTS` | A противоречит B |
| `DEPENDS_ON` | A зависит от B (без B A не работает) |
| `EXTENDS` | A расширяет B (добавляет измерение, не отменяя B) |
 
Атрибуты ребра:
 
- **type** — тип из фиксированного множества.
- **weight** — вещественный коэффициент силы связи [0.0 — 1.0].
- **identity_degree** — дополнительный атрибут для рёбер типа `IDENTITY` [0.0 — 1.0]. Различает полное тождество (1.0), контекстное тождество, операциональную эквивалентность и приблизительное сходство (ближе к 0.0). Защита от ложного схлопывания синонимии.
- **source** — ссылка на происхождение связи.
- **created_at** — момент создания.
- **updated_at** — момент последнего изменения.
- **valid_from / valid_to** — временной интервал актуальности (null означает бессрочность).
 
### 5.4. Временная ось
 
Временная ось — часть логики графа, а не метаданные.
 
Одно и то же ребро в разные моменты может иметь разный вес. Это не два разных ребра, а одно ребро с историей. Реализация — через версионирование: каждое изменение веса или статуса ребра создаёт запись в истории, предыдущее значение сохраняется.
 
Временная ось позволяет:
 
- Восстановить состояние графа на любой момент в прошлом.
- Отследить, как менялась связь между понятиями.
- Различить актуальное знание и историческое.
 
Это предотвращает комбинаторный рост графа при сохранении полной траектории изменений.
 
## 6. Оператор LLM
 
### 6.1. Принцип работы
 
Оператор графа — отдельная LLM в бэкенде. Не агент. Не tool для агента. Имеет прямой доступ к данным через программную обвязку.
 
Это один и тот же LLM с разными промптами для разных операций (проекция, ingestion, обновление). Точка одна.
 
Аналогия: вырожденная воля (термостат). Инерция связей, а не инерция смыслов.
 
### 6.2. Ключевое разграничение
 
Оператору **не запрещено** читать запрос на естественном языке. Ему **запрещено** интерпретировать содержание узлов графа.
 
Запрос — входной сигнал, по которому оператор определяет точку входа. Оператор сопоставляет слова запроса с содержанием узлов для нахождения точки входа, но не строит смысл из содержания узлов между собой.
 
Аналогия: поиск книги в библиотеке. Читаешь названия на корешках, чтобы найти нужную. Но не читаешь сами книги и не строишь из них новое знание. Находишь точку входа и дальше работаешь со структурой каталога.
 
### 6.3. Допустимые операции
 
**Проекция (чтение):**
 
- Получение сырых данных из базы (подготовленных обвязкой).
- Формирование граф-проекции в JSON из полученных данных.
- Ограничение глубины разворачивания по весам и расстоянию.
 
**Ingestion (запись):**
 
- Извлечение узлов и рёбер из входящего материала (диалог, документ, текст). Source anchor заполняется автоматически.
- Слияние: новые узлы сопоставляются с существующими. Совпадение — обновление веса, timestamp, source. Конфликт — создание ребра `CONFLICTS`. Новый узел — добавление.
- Обновление весов: при поступлении подтверждающей или опровергающей информации — пересчёт confidence и weight.
- Удаление: узлы с confidence ниже порога в течение длительного времени и без высоковесных рёбер — кандидаты. Удаление только по явному сигналу, не автоматическое.
 
После каждой операции записи — валидация (раздел 8).
 
### 6.4. Запрещённые операции
 
- Интерпретация содержания узлов (за исключением нахождения точки входа).
- Оценка «важности» на основании семантики.
- Построение новых смысловых связей, не существующих в данных.
- Перефразирование содержания узлов.
 
## 7. Сериализация
 
### 7.1. Формат — JSON с жёсткой схемой
 
Не DSL, не естественный язык. JSON выбран по следующим основаниям:
 
- **Валидируемость.** JSON Schema обеспечивает автоматическую проверку структуры. При ошибке — точная диагностика нарушения.
- **Однозначность.** Связи выражены явно, не допускают переинтерпретации.
- **Расширяемость.** Новые атрибуты добавляются без ломки формата.
- **Совместимость.** LLM обучена на огромном корпусе JSON и обрабатывает его с минимальными потерями.
- **Компактность.** Существенно меньше токенов, чем XML, при тех же гарантиях.
- **Алгоритмическая проверяемость.** Язык разметки гарантирует от неверной структуры. При формировании сложных связей возможны галлюцинации LLM, приводящие к слому структуры. Сломанный JSON детектируется алгоритмически и возвращается на перегенерацию с изменённым промптом.
 
Структуру JSON-схемы зафиксировать жёстко. Набор типов рёбер, набор полей узла, диапазон весов — определяется один раз и валидируется автоматически.
 
### 7.2. Пример структуры
 
```json
{
  "projection_context": "запрос о связи воли и перехода",
  "timestamp": "2026-04-13T15:30:00Z",
  "nodes": [
    {
      "id": "n001",
      "content": "Воля",
      "confidence": 0.95,
      "source": "treatise:ch3:para7"
    },
    {
      "id": "n002",
      "content": "Переход между положениями в смысловых измерениях",
      "confidence": 0.95,
      "source": "treatise:ch3:para8"
    },
    {
      "id": "n003",
      "content": "Инерция перехода",
      "confidence": 0.90,
      "source": "dialogue:2026-04-13:session42"
    }
  ],
  "edges": [
    {
      "type": "PART_OF",
      "source": "n001",
      "target": "n002",
      "weight": 0.95,
      "origin": "treatise:ch3:para7"
    },
    {
      "type": "IDENTITY",
      "source": "n001",
      "target": "n003",
      "weight": 0.85,
      "identity_degree": 0.70,
      "origin": "dialogue:2026-04-13:session42"
    }
  ]
}
```
 
В этом примере: воля является частью перехода (не тождественна ему). Воля и инерция перехода — операционально эквивалентны (identity_degree 0.70), но не полностью тождественны. Целевая LLM получает эту структуру и видит связи явно, без необходимости достраивать их самостоятельно.
 
## 8. Контур валидации
 
Двухуровневая алгоритмическая валидация. Оба уровня работают без интерпретации содержания.
 
### 8.1. Первый уровень — структурная валидация (JSON Schema)
 
- Все обязательные поля присутствуют.
- Типы рёбер принадлежат фиксированному множеству.
- Веса и коэффициенты лежат в допустимом диапазоне [0.0 — 1.0].
- Идентификаторы узлов в рёбрах ссылаются на существующие узлы.
- Временные метки валидны.
 
Выполняется мгновенно, одним вызовом валидатора.
 
### 8.2. Второй уровень — графовая валидация (алгоритмический обход)
 
- **Связность проекции.** Проекция должна быть связной — нет изолированных подграфов внутри одной проекции. Для всего графа в целом изолированные компоненты допустимы — они ждут связи, которая может появиться позже.
- **Противоречия.** Нет одновременных `IDENTITY(A,B)` и `NOT_IDENTICAL(A,B)`.
- **Циклы.** Нет петель в рёбрах `PART_OF` (A часть B, B часть A).
- **Весовые аномалии.** Узлы с низкой достоверностью, на которые ссылаются рёбра с высоким весом, формируют **anomaly signal**, а не ошибку валидации. Сигнал включается в отчёт, но не блокирует проекцию. Спорный, но структурно важный узел не должен отбрасываться.
- **Темпоральная консистентность.** Нет рёбер с `valid_to` в прошлом, включённых в текущую проекцию.
 
### 8.3. Контур коррекции
 
При невалидности на любом из уровней:
 
1. Ошибка формализуется (какое именно правило нарушено, какой узел или ребро).
2. Ошибка возвращается оператору LLM в промпте.
3. Оператор генерирует исправленную проекцию.
4. Повторная валидация.
 
Контур работает автоматически, без участия человека, без интерпретации содержания. Максимальное число итераций ограничено (например, 3), после чего система сигнализирует о неразрешимой ошибке.
 
## 9. Критически важные связи
 
Экспериментально установлено, что основная доля редукционных ошибок LLM приходится на два типа связей:
 
1. **«A есть B, выраженное иначе»** — ложные тождества. LLM схлопывает различное в одно.
2. **«A является частью B, но не тождественно B»** — ложные разделения или ложные отождествления части с целым.
 
Поэтому рёбра типов `IDENTITY`, `PART_OF` и `NOT_IDENTICAL` являются приоритетными при формировании проекции. Оператор должен включать их в проекцию всегда, когда запрошенные узлы связаны рёбрами этих типов, независимо от глубины разворачивания.
 
## 10. Ingestion path
 
### 10.1. Дисциплина ingestion
 
Качество системы определяется не только проекцией, но и дисциплиной записи в граф.
 
### 10.2. Операции записи
 
Все операции записи выполняются тем же оператором LLM с другим промптом. Отдельные процессы только валидируют и при необходимости возвращают на перегенерацию.
 
**Извлечение.** Из входящего материала оператор выделяет узлы и рёбра. Формирует JSON-структуру. Source anchor заполняется автоматически.
 
**Слияние.** Новые узлы сопоставляются с существующими:
 
- Совпадение → обновление weight, timestamp, source.
- Конфликт → создание ребра `CONFLICTS` между новым и существующим.
- Новый узел → добавление.
 
**Обновление весов.** Подтверждающая информация → рост confidence. Опровергающая → снижение.
 
**Удаление.** Узлы с confidence ниже порога в течение длительного времени и без высоковесных рёбер — кандидаты. Удаление только по явному сигналу, не автоматическое.
 
### 10.3. Разрешение конфликтов
 
При появлении нового знания, противоречащего существующему:
 
- Не удалять старый узел автоматически.
- Создать ребро `CONFLICTS`.
- Скорректировать confidence обоих узлов.
- При последующих обращениях агент видит конфликт явно и может принять решение.
 
### 10.4. Валидация после записи
 
Каждая операция записи проходит тот же двухуровневый валидатор (раздел 8). Не прошла — обратно оператору с другим промптом.
 
## 11. Принципы из концепции личности, применённые как спецификация
 
| Принцип из трактата | Применение в архитектуре |
|---|---|
| Текущий контекст не подлежит компрессии | Проекция, переданная в контекст целевой LLM, не сжимается далее |
| За пределами контекста — семантически управляемое сжатие с сохранением направленности | Оператор решает, что развернуть, а что передать как указание на связь |
| Память сохраняет не буквальность, а смысловую направленность | Граф хранит связи и веса, а не полные тексты всех разговоров |
| Конструкция не допускает редукции | Формат сериализации делает связи явными, не оставляя их на достраивание целевой LLM |
| Воля — инерция перехода, инвариантная ко времени | Временная ось графа сохраняет историю изменений, не создавая дубликатов |
| Различение возможно только в пространстве определения | Типизация рёбер задаёт пространство, в котором связи могут быть различены |
 
## 12. Реализация
 
### 12.1. Объём изменений
 
Минимальный. Существующий конвейер Memory Box (выборка данных, tools для агента, auto-linking, graph traversal, lifecycle management) не затрагивается. Добавляется одно звено между результатом выборки и передачей в контекст агента.
 
### 12.2. Шаги реализации
 
1. Определить JSON Schema для граф-проекций.
2. Реализовать двухуровневый валидатор (структурный + графовый).
3. Реализовать оператор LLM: промпт для проекции, промпт для ingestion.
4. Встроить оператор в точку между выборкой и передачей агенту.
5. Провести эксперимент: загрузить трактат «Я есть» в граф, сформировать проекцию, передать целевой LLM, проверить, воспроизводятся ли редукционные ошибки.
6. По результатам эксперимента — откалибровать пороги весов, глубину разворачивания, приоритеты типов рёбер, достаточность одного коэффициента confidence.
 
### 12.3. Расширение таблицы relations или новая таблица
 
Решение принимается при реализации. Существующая таблица `relations` обслуживает ассоциативный граф (auto-linking, co-retrieval, Hebbian reinforcement). Структурный граф может использовать ту же таблицу с новыми типами рёбер или отдельную таблицу. Критерий выбора: не должно сломать существующий auto-linking и consolidation sweep.
